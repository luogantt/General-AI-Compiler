native/lib/DeviceLowering.cpp

从第一性原理理解 DeviceLowering

它不是“在图上连线”。它只回答五个问题：这张图能不能跑？按什么顺序跑？ 数据住在哪？每个算子由谁算？Runtime 怎么启动？ 把这些问题拆开，就是下面六个不可再少的步骤。

DeviceLowering = 合法性谓词 + DAG 线性化 + 生命周期内存分配 + 实现选择 + Kernel 构造 + 合同序列化
输入：ModuleOp
一张 tensor DAG：算子节点 + SSA 值 + 权重常量
↓先判断能不能做
01

合法性：这张图能在目标上执行吗？

合法性谓词

设备后端不是万能的：它只支持固定算子、静态 shape、特定 dtype 和属性模式。 这一步在分配任何内存、生成任何 Kernel 之前，把不支持的形态全部拒绝。 拒绝是编译错误，不是运行时回退。

validateDeviceGraph() preflight() validatePad()
↓把图变成可执行顺序
02

线性化：把 DAG 变成 dispatch 序列

顺序从哪来？

GPU/NPU Runtime 执行的是队列，不是图。所以每个产生 SSA 值的算子变成一个 dispatch；每个 dispatch 恰好产生一个输出张量。按拓扑顺序排列， 并记录每个 dispatch 依赖哪个前序 dispatch。

dispatch loop producer depends_on
↓每个值需要一个地址
03

内存映射：每个 SSA 值住在哪？

地址与生命周期

设备全局内存有限，不能运行时 malloc。这里把每个 SSA 值映射成 物理 Buffer：输入/常量独立分配，中间值进入 64 字节对齐的 arena。 按最后一次使用决定复用：只有 last_use < new_producer 才能覆盖。

TensorAllocation tensorSize() view elision arena allocator
↓同一个数学，有多种实现
04

实现选择：每个算子由谁算？

选择哪条后端路径

规则算子可以变成 Linalg 结构化循环；不规则算子需要专用标量发射； 形状合适的 MatMul/Conv 可以走设备模板；满足严格合同的 Linalg 子图可以交给 Triton。 选择失败就保留 native，并记录原因。

templates::select() Triton selection isLinalgDeviceOperation()
↓把选择变成设备函数
05

Kernel 构造：设备函数长什么样？

指针 + 线程号 → 输出

一个 Kernel 就是一个函数：参数是若干全局指针，线程号 tid 决定 当前线程算哪个输出元素。规则 Linalg 走 destination bufferization + Linalg-to-SCF； 不规则算子走 emitElement/emitSpatial；模板和 Triton 只替换函数体。

emitElement() emitSpatial() emitLinalgDeviceElement() templates::emit()
↓Runtime 不读 MLIR，只读合同
06

合同序列化：Runtime 怎么启动？

plan.json

把 tensor 表、offset、dispatch 顺序、依赖、launch 几何和 target 字段写成 plan.json。Runtime 只认这份合同，并且会在打开设备前重新校验一遍。

manifest tensors / inputs / outputs parsePlan()
↓设备执行
输出：Kernel 机器码 + plan.json
Runtime 分配/上传 → 按 dispatch 顺序启动 → 下载输出

为什么必须是这六步

每一步都在消除一个不可避免的不确定性。少一步，后面的信息就不够。

01 合法性：因为设备不是图灵完备的

设备 Kernel 只能处理它理解的语义。动态 shape 无法计算静态地址； 未支持的属性模式无法安全猜测；不是所有 ONNX 算子都能在设备上执行。 所以必须先有一个“可执行性谓词”，把不可执行的图挡在 codegen 之前。

这也是为什么 preflight() 既检查算子白名单，也检查静态 shape、 dtype、ScatterND 索引、Gather 越界、LayerNorm 精度模式等。

validateDeviceGraph() preflight()

02 线性化：因为 Runtime 执行的是队列

DAG 只是编译期的依赖关系；设备端没有“图调度器”。把每个输出值的生产者 变成一个 dispatch，就把“图”变成了“按顺序提交的 Kernel 列表”。 每个 dispatch 只有一个输出，所以输入/输出绑定是唯一的，Buffer 生命周期也容易证明。

依赖仍然保留：depends_on 记录前序 dispatch，Runtime 可以检查顺序， 内存复用也依赖这个顺序。

dispatch loop depends_on

03 内存映射：因为设备端不能 malloc

所有 Kernel 都通过 64 位（CUDA）或 RV32（Vortex）指针访问全局内存。 指针必须在编译期确定，所以每个 SSA 值都要有一个固定 offset。 中间值共享一个 arena，用生命周期决定能否复用；图输出必须活到最后。

这就是 last_use < new_producer 规则的来源：如果前一个值在 dispatch i 还在被读，就不能把它的地址在同一个 dispatch 里分给新输出。

last-use / arena allocator manifest tensor offsets

04 实现选择：因为同一个数学有多种最优实现

MatMul 可以是标量三重循环，也可以是 shared-memory tile；Softmax 可以是 单线程串行归约，也可以是 CTA 协作归约；一些规则 Linalg 子图还可以整体交给 Triton。 选择依据是形状、dtype、目标资源和严格合同，而不是“哪个名字好听”。

选择失败不会换后端，而是保留 native 标量路径，并把原因写进 manifest。 这让每个 dispatch 的实现来源可审计。

templates::select() Triton selection dispatch["lowering"]

05 Kernel 构造：因为设备函数只认指针和线程号

一个 Kernel 的 ABI 不是“算子”，而是“指针数组 + 线程号”。 线程号决定当前线程负责哪个输出元素；Kernel 内部用广播、归约或采样 把这个元素算出来。Linalg 路径复用上游 Linalg-to-SCF； 非规则路径用 ScalarBuilder 逐条创建 typed MLIR Operation。

模板和 Triton 只替换 Kernel body，不改变 Buffer 规划、dispatch 顺序和 ABI。 这就是为什么它们可以“插进来”而不影响正确性。

emitElement() emitSpatial() emitLinalgDeviceElement()

06 合同序列化：因为 Runtime 不理解编译器 IR

Runtime 不解析 MLIR，也不重新推导 shape。它需要一份稳定的 JSON： 每个 tensor 的名字、dtype、字节数、storage、offset；每个 dispatch 的 kernel、 inputs、output、依赖、launch 几何。这份 JSON 就是 plan.json。

Runtime 还会重新校验：活跃区间不能重叠、Triton 几何必须和 shape 一致、 CUDA/Vortex 的 ABI 字段必须匹配。manifest 是合同，不是日志。

manifest parsePlan()

用一张小图走完全流程

这是把上面的六步落到具体数据上的方式。看懂这个例子，就看懂了 DeviceLowering 在做什么。 

%A = input  tensor<4xf32>
%B = input  tensor<4xf32>

%T = gac.add   %A, %B   // dispatch 0
%Y = gac.relu  %T       // dispatch 1

return %Y
  1. 合法性：add/relu 都在白名单里；shape 是静态 4；dtype 是 FP32。通过。
  2. 线性化：产生两个 dispatch。dispatch 0 输出 %T，dispatch 1 输出 %Y；dispatch 1 依赖 0。
  3. 内存映射：%A/%B 是输入 Buffer；%T 进 arena，offset 0；%Y 是图输出，offset 64（64B 对齐），活到所有 dispatch 结束。
  4. 实现选择：add/relu 是规则逐元素算子，默认走 Linalg pointwise；也可以显式选择 legacy 标量路径。
  5. Kernel 构造：add_kernel(ptrA, ptrB, ptrT) 和 relu_kernel(ptrT, ptrY)；每个线程处理一个元素。
  6. 合同：manifest 记录 %T offset=0、%Y offset=64、dispatch 0/1 的顺序和依赖；Runtime 按顺序启动两个 Kernel。

几个容易搞反的点

这些是理解 DeviceLowering 时最常见的误解。

  • 不是把整张图做成一个大 Kernel。每个输出张量一个 dispatch；Kernel 之间用全局 Buffer 交接。
  • 不是运行时分配内存。所有 offset 在编译期确定；Runtime 只按 manifest 映射地址。
  • 不是所有算子走同一条路径。规则 Linalg、专用标量、设备模板、Triton 是四种不同的 Kernel 来源。
  • 不是 manifest 只是调试日志。它是 Runtime 的唯一执行合同，并且会被重新校验。
  • 不是先选模板再分内存。Buffer 生命周期和实现选择是解耦的；模板/Triton 不改变 Buffer 规划。
  • 不是“编译失败就换后端”。选择失败会保留 native 标量路径，并记录原因，不会静默切换。
一句话总结：DeviceLowering 把“张量图”变成“一串带指针和线程号的 Kernel + 一张全局内存地图 + 一份 Runtime 能执行的合同”。 代码位置以当前工作树为准。
